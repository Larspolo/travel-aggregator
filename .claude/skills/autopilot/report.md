# Autopilot: the run report (step 8)

Read this file before the report of step 8 (part of the `autopilot` skill, #1700).

No open issue with label `agent-status` (step 1.1): make it (title "Agent status", body: the state comment below and
an empty `### Process changes`). The dashboard workflow fills in the rest.

The dashboard in the body of the status issue is generated by `framework/tools/dashboard.py`. Run `python3 framework/tools/dashboard.py`
after your report (the workflow `dashboard.yml` runs it every 10 minutes, #2168). Do not write
"Waiting for you", "Working on", "Next up" or "Recently done": the script makes them from GitHub.
`framework/tools/report.py --post` (below) sets the state comment: `last_run` now and `runs` + 1, the other keys stay
(`last_review`, `review_prs`, `last_roadmap`: the reviews, #898, #2039; #1701). Do not edit it by hand.
In the body, change only one part by hand and keep the rest as it is (read the body just before the change,
other runs change it too):
- The section `### Process changes`: add a line `- <date>: <what changed in the skills, CLAUDE.md or
  LEARNINGS> (PR #n) — before: <numbers>` at the top, keep the last 5. When the change targets a number of
  `framework/tools/health.py` (phase minutes, conflicts, takeovers, quota per PR), write that number now for the last 50 merged
  PRs (`framework/tools/health.py`, for example "report 10 % of the run minutes / 50 PRs"), so that the `improve` skill can
  check it later on the same amount of work (#1738, #2039). A pitfall line
  (`docs/LEARNINGS.md`, a doc line) gets `— before: -`.

Then add one short report: what you did and what is next. `--post` adds it to the branch `metrics` (`runs/`), not as
a comment on the status issue (2026-10-29; only when no push goes through, it comments). Write it with one command (#1701): `python3 framework/tools/report.py --usage "<the Usage: line of step 1.2 or of the brief>" --text "<what you
did, what is next>" --ticket N --size S --result "pr #M" --checks K --checks-min C --sinks "<list or none>"
--post` (repeat the ticket options for each ticket,
in the same order). It adds the release bar, the `Tokens:` line and the footer in the format below. Without `--post`
it only prints the report. A question for the owner goes on its
issue, not here (`owner.md`).
End it with one metrics line for each ticket of the run (the `improve` skill reads these lines):

    Metrics: ticket #<n> · <size> · <merged|pr #n|closed|checked|blocked|needs-human|none> · <minutes> min · setup <m> min · checks <k> · checks <c> min · time sinks: <list or "none"> · phases read <m> · claim <m> · code <m> · verify <m> · ci <m> · conflict <m> · report <m>

Example: `Metrics: ticket #876 · size:S · merged · 45 min · setup 0 min · checks 2 · checks 6 min · time sinks: none ·
phases read 8 · claim 1 · code 18 · verify 9 · ci 0 · conflict 5 · report 4` (one line).

Result (`report.py` stops any other form): `pr #n` when you pushed PR #n and Automerge merges it later (the usual case: you report before the merge);
`closed` when you finished the ticket with no PR (a check ticket with the label `close`, 2026-10-29: 80 of 345 tickets
said `none`, most of them such checks); `checked` when a check ticket (or a deep-lane split or epic check) ran
and put its findings on the ticket (a comment, new bug tickets, `Depends on`) and the ticket stays open by design (#5782:
8 of 18 given-back runs were such checks); `none` only when the run stopped without a PR and the ticket stays open.
Before you give back a ticket whose next step only the owner can do, add `needs-human` (`owner.md`): with `none` and
a release only, the next run takes it again in minutes (#5676: 2 runs).
When your PR closes the last ticket of a line `- After #a, #b: ...` in the section `## Owner checks` of its epic,
lock it with `python3 framework/tools/claim.py E --ownercheck --state a` (exit 1: another run makes it, skip it; #1797: two runs made one check twice), then
make that `needs-human` ticket now (`ticket` skill) with only the steps that no agent can do (do the other checks
yourself first and link the evidence) with `parent: E` (a sub-issue of the epic: else the epic has no open sub-issue, and the pacer starts epic checks for it, #432), so the owner can check when the merge is live (owner, 2026-11-06). `framework/tools/health.py` counts the `pr #n` lines by the present PR state (#902).
`framework/tools/report.py` puts the output of `python3 tools/release.py` (the release bar of each goal, #879) above the
`Usage:` line, when the project has that tool (#1963).
Below the metrics lines, `report.py` adds the `Tokens:` line (the tokens of this session and its largest sinks), the
`Calls:` line and the `Run:` line (the session, the start, the model, the eq of each phase and ticket, the lane): do not
run `tokens.py` yourself (owner, 2026-11-06: one call fewer at the end of the run, where each call costs the most). `framework/tools/health.py` adds these lines, and the
`improve` skill uses them as one source to find the bottleneck.
Put the `Usage:` line of step 1.2 (or of the brief of the pacer) above the metrics lines, unchanged: `framework/tools/health.py` measures the quota use of one
run per hour from pairs of these lines, and `framework/tools/usage.py --target` uses that value (#462).
`setup`: minutes from the start of the run to the claim of the first ticket (0 for later tickets). `report.py`
measures it in the transcript: do not give `--setup`.
`checks <k>`: rounds of the `verify` skill before the push; `checks <c> min`: their minutes in total.
`phases` (#899): whole minutes of the ticket in each phase. `report.py` measures them in the transcript
(`tokens.py --phases`): do not give `--phases` (the guesses of the runs were 2 to 6 times too large, 2026-10-28). `read` (feedback, triage, the ticket and the code), `claim` (pick and claim), `code` (change and tests),
`verify` (the checks of the `verify` skill), `ci` (wait for or fix CI after the push), `conflict` (merges with main),
`report` (PR text, run report, process step 9). Keep the fields in this order: `framework/tools/health.py` sums them.

Do not post a report when nothing changed.
